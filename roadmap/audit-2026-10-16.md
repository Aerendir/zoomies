### Verdict

The code is in unusually good shape for its age and size: formatting, vet and staticcheck are clean, there is one TODO in 466,000 lines of Go, no commented-out code, no utility dumping grounds, the package boundaries in `AGENTS.md` hold in production code, and duplication is rare. The weak points are all where process meets people: the release process has just shipped a tag the project's own updater refuses, a fresh checkout does not build and the one document that says so is not the one a contributor reads, several test suites exist that CI never runs, and the planning documents contradict each other about which of them is current.

Three things need a person's attention before any cleanup PR, because they are live or outward-facing: **C1** (the release tags), **H2** (the generated branch that every clone downloads) and the stray files the docs sweep left on this machine (see "Limitations and loose ends" at the end).

## 1. Critical

### C1. The latest GitHub release is a tag the project's own updater will not offer

**Pass:** Maintainer review

**Where:** `.github/workflows/release.yml:60-66` (the tag guard), `internal/updates/release.go:55-59` (`tagPattern`, `ValidTag`) and `:196-199` (`eligible`), `internal/version/compare.go:87-110` (`parseRelease`), GitHub releases `v1.3.6` and `v1.3.6.1`.

**Problem:** The release workflow's only shape check is `case "$TAG" in v*)`. The updater accepts exactly `^v[0-9]+\.[0-9]+\.[0-9]+$` and, in `eligible`, also requires the release to carry assets. The two disagree, and on 15 October the gap was used:

- `v1.3.6` was published at 12:51 UTC, its release workflow run failed, and the release has **0 assets**.
- `v1.3.6.1` was published at 13:09 UTC as the recovery, its run succeeded, it has 9 assets and is now GitHub's "Latest".
- Reproduced: `ValidTag("v1.3.6.1")` is `false`, and `version.CompareBuilds("v1.3.6.1", "v1.3.6")` is `differs`, so the version package cannot order it.
- So the newest release the updater can offer is `v1.3.5` (`eligible` needs a valid tag and a complete asset set; I read the tag half and checked the asset counts with `gh`, but did not read `Complete` itself). A controller on `v1.3.5` has no update to take, while `install.sh` resolves `latest` through the `/releases/latest` redirect, which now names `v1.3.6.1`, a version string the skew checks treat as unrelated to anything.
- The workflow also refuses to rebuild a published release by dispatch, so a failed run on a published tag has no documented recovery. A four-part tag was the workaround, and there is no written release process or tag policy anywhere (H14).
- `V1.1.0` (capital V) is also published with 0 assets. The workflow's own comments record why: an earlier trigger matched `v*`, so a capital V built nothing and the release went out empty.

Not tested end to end: what a running controller on `v1.3.5` or `v1.3.6` actually shows on its Updates page. **Needs confirmation.**

**Fix:**
1. Decide how to repair the current state. The straightforward route is to cut `v1.3.7` through the normal path so a valid, complete release is the newest. Moving or deleting existing tags and releases is outward-facing and is the owner's call.
2. Make the `setup` job in `release.yml` refuse any tag that `ValidTag` would refuse (three numbers, with the existing hyphen rule for pre-releases), with the same wording style as the current error.
3. Add a test in `internal/docs` that keeps the workflow's pattern and `updates.ValidTag` in step (it can read the pattern out of the workflow, as the existing workflow tests do).
4. Write the release procedure down (see H14), including what to do when the build fails after publication.

**Risk:** Steps 2 to 4 are safe and mechanical. Step 1 changes what users download; confirm with the owner first. Run a dry release on a pre-release tag before relying on the new guard.

### C2. A fresh checkout does not build, and the contributor-facing docs hide it

**Pass:** New contributor walkthrough

**Where:** `internal/api/web.go:21-30`, `Makefile` (`test`, `test-short`, `cover`, `lint`, `generate`, `ui-dev`), `README.md` (quick start), `CONTRIBUTING.md:31` and `:60`, `AGENTS.md:36`.

**Problem:** `internal/api` embeds `internal/api/webdist`, which is a gitignored build product. In a clean `git archive` copy, `go vet ./internal/api` and `go test ./internal/api` fail with `pattern all:webdist: no matching files found` (reported by the docs sweep, and `AGENTS.md` says the same). Only `AGENTS.md` explains the fix, and that file is written for agents. In detail:

- `README.md` never mentions `make build-nogui`. `CONTRIBUTING.md:60` calls it a "fast inner loop", not a required first step.
- The comment on the embed in `internal/api/web.go` says the placeholder means "this embed never fails on a fresh checkout". It does fail: the placeholder is written by the Makefile, not committed.
- `make test`, `make test-short` and `make cover` have no prerequisite that writes the placeholder. `make generate` runs `go run ./cmd/zoomies`, which compiles the same package.
- `make lint` has an order-only prerequisite on `web/node_modules` and so runs `npm ci`, yet `CONTRIBUTING.md:31` says Node is only for UI work. `make ui-dev` has no such prerequisite and dies with `vite: not found` on a fresh tree.
- Reproduced: after `make build-nogui`, the build, lint, UI check and unit tests all pass, so the fix is cheap once known.

**Fix:**
1. Add the placeholder as an order-only prerequisite (`| $(UI_OUT)/.placeholder`, the file target `build-nogui` already uses) to `test`, `test-short`, `cover`, `lint` and `generate`. (`test-drill` and `test-upgrade` already depend on `build-nogui`.) Add `| $(UI_DIR)/node_modules` to `ui-dev`.
2. Correct the comment in `internal/api/web.go`.
3. Add a "First build" step (`make build-nogui`, then `npm ci` in `web/` if you will touch the UI) to both `README.md` and `CONTRIBUTING.md`, and say that `make lint` installs UI dependencies.

**Risk:** Low. A Makefile edit runs the whole CI once. The prerequisite is an existing file target, so there is no new mechanism.

### C3. The Compose quick start leaves out a directory the Compose file will not create

## 2. High impact

### H1. Tests that exist but CI never runs

**Pass:** Maintainer review

**Where:** `.github/workflows/ci.yml` (`ui` job at about `:674-708`, `other` Playwright shard at about `:810`, `rest` Go shard), `Makefile:223-225`, `web/package.json:20`, `web/playwright.config.ts:85-112`, `.github/workflows/fuzz.yml`, `web/tsconfig.json`, `web/unit/assistant-markdown.test.ts:235-241`.

**Problem:** Five separate gates are written and not enforced:

- **UI unit tests.** `npm run test:unit` (939 tests) is not called by any workflow or Makefile target. Confirmed by grep for `test:unit|vitest` across `.github` and `Makefile`: empty. `CONTRIBUTING.md:121` tells contributors to run it, and `AGENTS.md` names `web/unit/absent-value.test.ts` as the guard for the UI's placeholder rule, so a guard the docs cite is never run. Reproduced: all 939 pass in about 9 seconds.
- **Build-tagged Go suites.** `go vet -tags e2e`, `-tags drill` and `-tags load` exist only inside `make lint`, which no workflow calls. Confirmed: no `-tags` in any workflow. The Makefile comment records the incident this guards against (a non-test file referring to a symbol only a test file defined). Vet passes today.
- **Playwright `transfer` and `transfer-mobile`.** They are excluded from the `chromium` and `mobile` projects and absent from the `other` list in CI. Confirmed by reading both files.
- **Fuzz targets.** Two of five (`FuzzCheckoutDepthEditPreservesTheDocument`, `FuzzDependencyInventoriesPreserveTheirRetainedInvariants`) are not in `fuzz.yml`'s matrix. Confirmed by grep. The workflow also hard-codes `runs-on: zoomies-linux-x64` on `pull_request`, without the fork selector `ci.yml` uses, so a fork's code would run on the fleet (the existing workflow test enforces the selector for `ci.yml` and `govulncheck.yml` only, reported).
- **Type-checking skips tests and scripts.** `web/tsconfig.json` includes `src/**`, `tests/**/*.ts` and `*.config.ts`, not `unit/`. The UI sweep reports 78 type errors in about 30 unit test files and 16 in `scripts/block-spacing.mjs` once included (not re-run by me).

Adding the unit tests to CI will meet one flaky test first: `assistant-markdown.test.ts` asserts a wall-clock bound (`< 5_000` ms) and failed once at 5.5 seconds under a load average of about 15 (reported; the assertion itself I read).

**Fix:**
1. Replace the wall-clock assertion with a growth check (parse N and 2N, assert the ratio), then add `npm run test:unit` to the `ui` job and a `make test-unit` target.
2. Add `go vet -tags e2e ./test/... && go vet -tags drill ./test/... && go vet -tags load ./test/...` to the `rest` Go shard.
3. Add `--project=transfer --project=transfer-mobile` to the `other` shard.
4. Add the two fuzz rows, the fork selector and a `workflow_dispatch` runner input to `fuzz.yml`, and extend the workflow test.
5. Add a `tsconfig.unit.json` (with `allowImportingTsExtensions`) to `npm run check` and fix the fixtures in a separate PR.

**Risk:** Low per step, but each can turn CI red for a real reason it was hiding (especially steps 3 and 5), so ship one gate per PR.

### H2. The generated `zoomies-ai-context` branch adds a 25.6 MiB file to history on every push to `main`

**Pass:** Maintainer review

**Where:** `.github/workflows/zoomies-ai-context.yml:452-454` (non-force publish), branch `origin/zoomies-ai-context`, `.zoomies/AI_CONTEXT.md`, `internal/aicontext/`.

**Problem:** The workflow publishes by creating a commit on top of the generated branch and fast-forwarding it (`'force': False`), keeping ownership checks and "the previous valid branch remains untouched" as safety properties. The cost is that the branch only grows:

- 348 commits since 3 October (about 29 a day), each carrying a new `snapshot.json` of 25.6 MiB. The twelve largest blobs in the whole repository history are all this file, and the 348 versions total 8.3 GiB uncompressed.
- `size-pack` in this clone is 261.5 MiB (plus 279.6 MiB of loose objects locally). By per-object on-disk size, the objects reachable only from this branch (about 330 MiB) outweigh everything reachable from `main` (about 189 MiB); those figures overlap with the loose objects, so read them as proportion, not as a clone size. A default `git clone` fetches every branch, so every new contributor and every CI checkout that does not shallow-clone pays for it.
- The file is the whole source tree as JSON ("code compression is disabled"), so it is redundant with the repository it describes.

This is a deliberate design (reads are pinned to a generated-branch commit so "a later publication cannot mix revisions"), so changing it is a maintainer decision, not a bug fix.

**Fix:** Pick one, in order of cost:
1. Tell contributors to clone with `--single-branch` or `--depth 1` (README and CONTRIBUTING), and set `fetch-depth: 1` where a workflow checks out. No design change.
2. Keep the safe-publish checks but reset the branch to a single parentless commit on a schedule (for example weekly), so history is bounded while a pin stays valid for a week.
3. Publish the snapshot as a release asset or workflow artifact and keep only the manifest on a branch.

**Risk:** Option 1 is safe. Options 2 and 3 change a documented contract (`.zoomies/AI_CONTEXT.md` tells assistants to pin to a generated-branch commit) and interact with the managed workflow (H3). Rewriting the existing branch is irreversible; take a backup first and ask the owner.

### H3. Dependabot and the managed AI Context workflow undo each other, and several things Dependabot should own are unowned

**Pass:** Maintainer review

**Where:** `.github/dependabot.yml`, `.github/workflows/zoomies-ai-context.yml:27,312,326`, `internal/aicontext/workflow.go:66-133`, `deploy/Dockerfile.runner`, `internal/naming/images.go:141-147`, `.github/workflows/ci.yml:664-671`.

**Problem:**
- **A revert loop.** The managed workflow is regenerated from `internal/aicontext/workflow.go`, which pins older actions than Dependabot's.
